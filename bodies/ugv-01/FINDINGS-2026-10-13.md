### 1a. ARGUS DRIVE module (CH340), from the spec and the team's encoder

Spec: `~/Desktop/ros2_new/docs/secret/ARGUS_DRIVE_Serial_Protocol_v4.1.3.pdf`,
six pages, 115200 8N1, LF terminated, written by a team member. Copied to
the session scratchpad. Command set:

| Cmd | Name | Args | Notes |
|---|---|---|---|
| 0x01 | INFO | none | reply `0x01;OK;040103` = 4.1.3 |
| 0x02 | ACCEL | 00-64 | still in the spec, but throttle has moved to the other board |
| 0x03 | BRAKE read | none | reply one hex word; 0.1 deg since 4.1.4 per the team's decoder, 0.1 percent per the 4.1.3 spec |
| 0x04 | STEER read | none | one hex word, 0.1 deg |
| 0x05 | STR_SW | 00 stop, 01 left, 02 right | limits and stall protection enforced |
| 0x06 | BRK_SW | 00 stop, 01 fwd (apply), 02 rev (release) | applying sets accel 0 and locks it |
| 0x07 | SPEED | 01, 02, 03 | speed mode; meaning not documented |
| 0x08 | GEAR | 01 D, 02 N, 03 R | |
| 0x09 | LIGHT | 00 off, 01 ring, 02 high, 03 low | one channel |
| 0x0A | IND | 00 off, 01 L, 02 R, 03 park | one channel |
| 0x0B | HORN | 01 0.5 s; 02, 03 locked | |
| 0x0C | RESET | none | restores outputs to defaults; defaults not documented |
| 0x0D, 0x0E | Wi-Fi | | locked by default; the module has a radio |
| 0x0F | BRK_LIM | read or set | limits readable, "not currently enforced" |
| 0x10 | STR_LIM | read or set | reply `0x10;OK;<min><max>`, 0.1 deg |
| 0x11 | LIM_EN | 00, 01 | locked by default |
| 0x12, 0x13 | admin steer, admin brake | | bypass limits; stall protection stays |
| 0x14 | STR_CTR | none | auto-centre, asynchronous reply |
| 0x16 | STATUS | none | all switch states; reply format not documented |

On the vehicle on 4 Oct the team found raw bytes are rejected
(`0x00;ERR;BAD_FORMAT`) and the ASCII form `0x01` is accepted. Their
encoder deliberately exposes only the operator vocabulary; admin, reset,
Wi-Fi and limit writes are not reachable from their console.

The spec contradicts itself in two places that the bench must settle
before either command is trusted (Codex finding A4): page 2 says "to
steer right send 0x05 01" while pages 3 and 5 say 01 is left; page 3 says
brake 00 is Stop while page 5 calls `0x06 00` "release brake" and the
team's code uses 02 for release. The team's encoder follows pages 3 and 5
and their 4 Oct observations, and is the better source, but it is still
unverified.

Not in the spec and not known: what the module does when the host goes
silent. No keepalive command exists. Whether a steering or brake move
started by 0x05/0x06 continues until a stop command, a limit, or a stall
is implied by the spec ("motion is stopped automatically when a limit is
reached or the actuator stalls") but not stated for the link-loss case.

### 1b. Accelerator board (FTDI), from the team's `accel_protocol.py` and `cmd_node.py`

Drives the accelerator PWM on "GPIO9". Duty 0 to 100 as a hex byte; the
team caps it at 90 on the host. Two statements in their code matter for
safety, both quoted from the docstrings:

- "The board resets when its port opens", so they wait 2.5 s before the
  first frame. That is consistent with Arduino auto-reset on DTR, but it
  is a host-code comment, not a measured waveform. Treat every port open
  as a possible reset; whether a close also resets depends on the driver
  and the board's circuit and is not established.
- "The board latches its last duty, so zero it before letting go." No
  firmware watchdog has been demonstrated on this board. A host that dies
  with duty above zero may leave the throttle where it was. This is the
  same hazard the August gate was written for, now on a different board.

The brake interlock the old firmware enforced (brake applied means throttle
rejected) is now enforced on the host in `accel_protocol.route()`, because
the accelerator board cannot see the brake.
